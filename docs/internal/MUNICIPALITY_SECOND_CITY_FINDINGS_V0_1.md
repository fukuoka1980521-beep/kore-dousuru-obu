# 2自治体目追加で分かったこと v0.1（内部用）

作成日: 2026-08-28
対象: 名古屋市版を参照実装として大府市版を作成した本Run全体を通じて得られた、
アーキテクチャ・データ・運用に関する知見。構造変更の詳細は [[OBU_DIFFERENCE_FINDINGS_V0_1]] を参照。

## A. 3自治体目追加時、コード変更なしでデータ追加だけで済みそうか

**結論: 高い確度で「済む」と評価する。** 今回の大府市版追加で必要だったコード変更は、

1. `municipalities/obu/config.json` と `municipalities/obu/data/*.json` の新規作成（データ追加）
2. `src/app/app.js` の config path を書き換え（1行、自治体切替の配線）
3. `app.js`/`core.js` に3箇所残っていた「名古屋市」のハードコード文字列を `state.config.display_name`
   参照に修正（新機能ではなく、名古屋市版実装時の見落としバグ修正）

の3種類のみだった。(2)は自治体ごとに別リポジトリ・別デプロイとする現在の構成では毎回必要になる
1行の変更であり、コード「構造」の変更ではない。(3)は今回で解消済みのため、3自治体目では
再発しない。したがって3自治体目は理論上、データ追加とconfig path変更だけで対応できる。

ただし条件がある: 3自治体目のデータが名古屋市・大府市と同じ `category` 命名規則
（「電池類」「発火性危険物」「粗大ごみ」等）を踏襲しない場合、`src/lib/freshness.js` の
`HIGH_RISK_CATEGORIES` 判定が機能しなくなる（[[OBU_DIFFERENCE_FINDINGS_V0_1]] 参照）。

## B. 自治体追加ごとにcomponent修正が必要か

**現時点では不要。** UIは `src/app/app.js` 1ファイルで、自治体固有の分岐を持たない設計になっている。
すべての自治体固有表示（名称・電話番号・優先ナビ・免責文言）は `config.json` 経由で注入される。
今回、component（UIロジック）側の修正はゼロ件だった（前述のハードコード修正3箇所を除く）。

## C. 自治体追加ごとに何時間程度の調査・入力が必要そうか

大府市版は以下の作業配分だった（概算、実測ベース）:

| 作業 | 所要時間の目安 | 備考 |
|---|---|---|
| 行政手続12件のリサーチ（サブエージェント実行時間） | 約5.5分 | 46回のツール呼び出し |
| ごみ品目48件のリサーチ（サブエージェント実行時間） | 約11分 | 49回のツール呼び出し |
| データのJSON化・スキーマ変換 | リサーチ結果を人手（AI）で変換、比較的高速 | 名古屋市版のスキーマが確定していたため機械的に変換可能 |
| 検索エイリアスの網羅性チェック・修正 | 自動チェックスクリプトで13品目・2手続の抜けを検出・修正 | この工程が無いと実際の検索で「ゼロ件」になる項目が複数残る |
| ブランド文字列の脱ハードコード | 3箇所 | 今後の自治体では発生しない（今回で解消済み） |
| テスト作成・調整 | 名古屋市版のテストをベースに大府市の実データに合わせて調整 | 名古屋市固有の前提（2026-10ルール変更等）を機械的に外す判断が必要 |

サブエージェントのリサーチ実行時間の合計は実時間で約16.5分（並列実行）。人手（AI側）の統合・検証
作業を含めた本Run全体は、調査→実装→テスト→監査まで通しでおよそ1時間強。3自治体目以降は
スキーマ・テスト構成が確立済みのため、実質的な追加コストは「対象自治体の公式情報リサーチ」と
「検索エイリアス網羅性チェック」の2工程に収束すると見込まれる。

## D. 公式サイト変更時、どこを更新すればよいか明確か

明確である。各レコードが `official_url` / `source_checked_at` / `status` を個別に持つため、
公式サイトの変更が確認された際は該当レコードだけを更新すればよい。加えて:

- 情報鮮度判定（`src/lib/freshness.js`）が `source_checked_at` を基準に自動的に「再確認期限切れ」を
  検出し、HIGH risk品目（電池類・発火性危険物・日付依存ルール）は30日、粗大ごみ等MEDIUMは90日、
  その他LOWは365日で自動的にレビュー対象としてUIに警告バナーを出す仕組みが既に機能している。
  大府市版でもこの仕組みは無改修で動作する（[[OBU_DIFFERENCE_FINDINGS_V0_1]] 参照）。
- `docs/obu/OBU_OFFICIAL_SOURCE_REGISTER.md` に出典URL・確認方法の台帳があるため、
  どのURLからどのレコードの情報を取得したかを追跡できる。

弱点: 台帳とデータの同期は今のところ手動である。件数が増えるとレコード側の `official_url` から
台帳側のエントリを逆引きする自動チェックは無い。3自治体目以降、件数が増える場合は
`scripts/check_public_sync.js` のような機械チェックの追加を検討する価値がある（ただし今回は
過剰実装を避け、見送った）。

## E. 将来の最大保守負荷は何か

1. **公式サイトのURL・ページ構造変更によるリンク切れ**: 大府市公式サイトはページIDベースの
   URL構造（例: `/kurashi/gomi/recycle/1029797.html`）で、名古屋市とはURL体系が異なる。
   自治体ごとにURL体系がバラバラなため、リンク切れ検知の自動化（section 12のような定期チェック）を
   将来的に自治体横断で回す仕組みが無いと、手作業でのリンク切れ発見に頼ることになる。
2. **「ごみ分別検索」のような動的検索ツールへの依存**: 大府市の主要な品目データ源は
   `ごみ分別検索`（JavaScript検索アプリ）で、多くの個別品目情報をここから取得した。この種の
   ページは将来リニューアルされるとURL・データ構造が丸ごと変わるリスクがあり、影響範囲が
   単一ページより広い。
3. **PDF内の文字コード問題によるデータ欠落**: 大府市の指定袋価格・プラスチック製品指定20品目の
   全リスト等は、案内パンフレットPDFに記載があると推定されるが、PDFの文字コードが特殊
   （Adobe-Japan1、ToUnicodeマップ欠落）でテキスト抽出できず、確認を断念した
   （`蛍光灯・蛍光管` `LED照明器具` の分別区分も同様に未確認のまま）。これは自治体側の
   PDF作成方法に起因する問題で、こちらの実装では解決できない。電話確認や画像OCR等、
   別手段でのフォローアップが必要になる。
4. **地域限定ルールの見落としリスク**: 大府市は「横根・北崎北尾地区」限定の生ごみ分別収集や、
   西地区／東地区で収集曜日が異なる等、地域差のあるルールを持つ。今回のデータは代表的な
   ルールのみを収録しており、全地域差を網羅していない。自治体が大きくなるほど、あるいは
   地域差の多い自治体ほど、この種の「一部の住民には当てはまらない」情報のリスクが増す。
5. **カテゴリ命名の自治体間不一致**（Aで前述）: 3自治体目のカテゴリ命名次第では
   `src/lib/freshness.js` のHIGH risk判定が機能しない可能性がある。

## 商品化・事業観点の所感（コード実装とは別の事実整理、section 17）

今回のタスク範囲では販売機能・SaaS化は実装していない。以下は今回の作業で見えた事実の整理のみ。

- **大府市で住民が金を払う必要があるサービスか**: いいえ。現状は無料の情報案内サイトであり、
  課金ポイントは無い。マネタイズは行政向け（自治体が費用を負担するモデル）が前提と見られる。
- **行政が導入する価値があるか**: ごみ分別・行政手続の問い合わせ削減という観点では、大府市は
  「ごみ分別検索」という類似の公式ツールを既に持っている（[[OBU_OFFICIAL_SOURCE_REGISTER.md]]
  参照）。したがって本サービスの価値は「新しい検索機能の提供」ではなく、「生活イベント起点の
  横断案内（ごみ・行政手続を1つの入口でまとめる）」「専門用語を先頭に出さない結論ファースト
  UI」「情報鮮度の自動管理」という、既存ツールが弱い部分の補完に見出すのが妥当。
- **既存手段（大府市公式のごみ分別検索等）との差**: 大府市の公式検索は品目ベースの単機能ツールで、
  行政手続・生活イベントとの横断案内は無い。本サービスは「引っ越してきた」のような生活の出来事
  から複数の手続・ごみ案内へ同時に到達できる点が差別化要素になり得る。
- **問い合わせ削減へ結びつきそうな箇所**: 家電リサイクル法対象品（テレビ・冷蔵庫等、市では
  収集しない）のように「市に電話して初めて『市では扱っていません』と言われる」典型的な
  問い合わせパターンに、検索結果の時点で明確に案内できる点。
- **誤案内事故リスク**: 大府市はUNCONFIRMED/PARTIALの品目・手続が名古屋市版より多い
  （蛍光灯・LED照明器具が完全UNCONFIRMED、児童手当・国保加入・マイナンバー住所変更等が
  PARTIAL）。これは大府市の公式サイトの情報構造が名古屋市ほど網羅的でない、または
  探索範囲内で発見できなかったことに起因する。fail-closed表示により誤案内は防いでいるが、
  UNCONFIRMED/PARTIALの比率が高いことは、公開前に自治体窓口への確認が必要な項目が
  相対的に多いことを意味する。
- **最大保守コスト**: 上記Eの1〜4（リンク切れ、動的検索ツール依存、PDF文字コード問題、
  地域限定ルール）が中心。自治体が増えるほど、この種の「自治体固有の情報取得しにくさ」への
  対応コストが線形に近い形で積み上がる可能性が高く、UI/ロジック側のコストではない。
